esp32-morse

M O R S E

Type a message on your phone. An ESP32-S3 sends it as Morse code on its LED, timed to the microsecond, then reports how long it took.

What it is

A small instrument with one job: to blink Morse code with timing you can predict on paper and then check. The board runs its own WiFi network and serves the app to your phone, so nothing is installed and no internet is involved. The phone chooses the message and the speed; the board does all the timing.

Why Morse? Its timing is defined exactly, by one unit, so every transmission comes with a prediction. Ten copies of the word PARIS at 10 words per minute must take 59.16 seconds, not 60, and the reason for the missing 0.84 s is a rule that is easy to get wrong. The point of the project is to make that prediction and test it with a stopwatch and a phone camera, not an oscilloscope.

The app itself runs only on the board, so there is no live link to it here. Below is an in-browser imitation of the LED, timed the same way.

How to use it

  1. Power the board from any USB port or charger.
  2. On your phone, join the WiFi network esp32-morse, password instrument. The password is published on purpose and protects nothing; it only stops a passer-by joining by accident. If the phone warns that the network has no internet, stay connected.
  3. Open http://192.168.4.1, typing the http://. There is no friendly name, only this address (see why).
  4. Type a message, choose a speed between 5 and 40 words per minute, and press Send.

What the app does

  • The board checks every character as you type. It accepts A–Z (lower case is upper-cased), 0–9, space and . , ? ' ! / ( ) & : ; = + - _ " $ @, up to 255 characters. Anything else is highlighted where it is, and Send stays disabled until it is gone. Nothing is silently dropped.
  • A live display follows the transmission at three levels: the whole message with the current word marked, the current character, and its dots and dashes with the one being sent lit.
  • The board's own time. When a transmission finishes, the app shows how long it took by the board's clock, next to the prediction.
  • Stop ends a transmission within one element, even in the middle of a long word gap. The message stays in the box, so pressing Send again repeats it.
  • An LED panel sets the colour and brightness, and warns when a setting will be hard to see or film. The filming preset, green at 20%, is the setting used for the slow-motion test, so that measurement can be repeated with identical conditions.
  • Up to four phones can connect at once. They all see the same transmission, and any of them can stop it.

How the timing works

Everything is a whole number of one unit, the dot:

elementlength
dot1 unit
dash3 units
gap between the dots and dashes of one character1 unit
gap between characters3 units
gap between words7 units

Speed is defined by the word PARIS, which is exactly 50 units including the word gap after it. W words per minute is 50W units in 60 seconds, so

dot (ms) = 1200 / WPM

At 20 WPM a dot is 60 ms and a dash 180 ms. At 40 WPM a dot is 30 ms; at 5 WPM, 240 ms.

Why ten PARIS take 59.16 s, not 60

PARIS is 50 units only if you count the word gap that follows it. A transmission ends with its last dot and sends no gap after it. So ten copies are

P A R I S     11+5+7+3+5 = 31
4 letter gaps      4 × 3 = 12
1 word gap after it      =  7
one PARIS                = 50 units

ten PARIS = 10 × 50 − 7  = 493 units
10 WPM: 493 × 120 ms = 59.16 s
 5 WPM: 493 × 240 ms = 118.32 s

The first version of this project's own plan predicted 60.0 s. The error was caught on paper, before any code was written. A host test now pins the number at exactly 493.

How the board keeps time

  • Absolute deadlines. Each dot, dash and gap ends at a deadline measured from the start of the transmission, using the chip's microsecond timer. Nothing is timed as "now plus a delay", so a late edge never pushes the next one back, and errors cannot accumulate over a long message.
  • A task of its own. The transmitter runs as a separate, high-priority task on the CPU core that is not handling WiFi. Between transmissions it sleeps and costs nothing.
  • Integer microseconds. A dot is 1200000 / WPM µs, computed with no floating point. The rounding is worst at 38 WPM: 0.95 µs per unit, or 0.003% of a transmission. At 5 and 10 WPM the division is exact.
  • One gap function. The 1, 3 and 7 appear in exactly one function in the firmware. Farnsworth timing, which stretches the gaps for learners, would change only that function.
  • A dark start. On Send, the LED goes dark for 200 ms before the first dot, even if it was lit by a colour preview. The first edge is therefore always dark to lit, which is what the stopwatch and the camera start from. Those 200 ms are not counted in the reported time.

From the phone to the LED

Phone — the app, served by the board, talking over a WebSocket
↓ message and speed  ·  ↑ progress and the board's time
Main loop — checks the request again, translates the whole message once, then hands it over
↓     ↑ a queue of events
Transmitter task — switches the LED at each deadline and records each element in the queue
↓
LED — the WS2812 on GPIO 48 that comes on the dev board; nothing else is wired

The transmitter never touches the network. It writes events into a 64-entry queue, about 3.4 s of headroom at 40 WPM, and the main loop sends them on. If a phone falls behind, the phone misses updates but the LED is never delayed. If the queue ever fills, the lost events are counted and reported, so a lost event cannot pass for ordinary WiFi lag.

The firmware does not trust the app. The app already blocks unsupported characters and out-of-range speeds, but the board checks every request again. This matters: a speed of 0 would reach 1200000 / WPM, and a division by zero reboots the chip. The same commands can be typed over the USB serial port, with no app involved, to show that the firmware refuses them by itself.

Why there is no name, only an address

A board can try to answer for a name such as esp32-morse.com by running its own DNS server, but modern phones often bypass it (Android's Private DNS, Chrome's DNS over HTTPS). A name that works only sometimes is worse than an address that always does.

What was verified

The tests below need nothing but eyes, a phone stopwatch and a phone's slow-motion camera. Each comes with a prediction made before the board was built.

Checked automatically, on every build

76 of 76 pass. The Morse table, the message rules and the timing arithmetic compile and run on an ordinary computer, with no board attached (pio test -e native). They check:

  • PARIS is exactly 50 units and ten PARIS exactly 493;
  • the digits follow their pattern rather than a copied list;
  • the letters most easily mistyped (Q, Y, F, L) against their known codes;
  • that a speed of 0, 4 or 41 WPM, a missing speed or 20.5 WPM is refused;
  • the 255-character limit;
  • that an emoji is reported at the right position.

The whole table of 54 characters was also compared with the international standard (ITU-R M.1677-1) and agrees, 54 of 54. Five of the punctuation marks, ! & ; _ $, are not in that standard; for those, the codes in common use are followed.

What these tests cannot tell you

Nothing here measures ±0.2% against an outside reference.

  • The stopwatch is coarse.
  • The board's reported time uses the board's own clock, so it would not notice if that crystal ran consistently fast or slow.
  • The video measures ratios, not absolute durations.

Together they catch every realistic way this could go wrong: a wrong constant, a missing or doubled gap, drift over a long message. A traceable absolute measurement would need an instrument this project deliberately does without.

Build one yourself

You need an ESP32-S3 N16R8 dev board with its RGB LED on GPIO 48, a USB-C data cable and PlatformIO. Nothing is wired to the board.

git clone https://github.com/semiconda/esp32-morse.git
cd esp32-morse/firmware
pio run -t upload

The app is compiled into the firmware, so there is a single upload. The README covers the rest: the first flash of a factory-fresh board, the serial commands, and running the tests.
